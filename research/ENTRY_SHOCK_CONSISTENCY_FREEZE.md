# Entry/held downside consistency: read-only falsification register

This is a diagnostic of the existing frozen `downside-shock-exit` rule, not a new wallet or strategy parameter. The three previously accepted reductions were selected historical development cases; their favorable outcomes are already known, so this is not a blind or forward test. The specific question is whether the same completed-day statistic was available when the **original macro entry decision** was made, and whether using it before entry would merely save an avoidable round trip or also discard other viable opportunities. No market or account order is authorized.

Before any new wallet or policy code, inspect all 50 original flat-to-flat first fills, including primary controls and every macro first fill. Use the original qualified Binance UM four-hour closes, the archived original fill-to-campaign attribution and the actual manual start/fill clocks. Evaluate the unchanged last-five versus last-20 completed-day downside-RMS `>1.5` condition at the first fill; a daily boundary crossed inside that session is unknown unless a prior-cycle checkpoint proves the entry-side input. Report source gaps separately. Join original realized net outcome only *after* counting the complete entry cohort, with winners and losers both visible; eventual outcome is diagnostic, never an input to a proposed rule.

For the two freshly paired fixed quarters, inspect **every archived observation cycle** in both baseline wallets, not only the successful held exits. Count unique flat `enter` opportunity identities, first accepted entry intents, IOC zero fills, repeated decisions within a session, and actual first fills. Give a reason for each difference between a shocked entry-side decision and a later held-side treatment: no first fill, different campaign, insufficient completed history, protective readback, timing, or stale/unknown state. Do not count polling cycles as independent opportunities. Compare candidate and baseline BUY/SELL identities and net wallet effects using the existing paired results. The archived 2023Q1 accepted wallet lacks retained per-cycle SQLite here; distinguish what its journal and final trades prove from what they cannot.

If this identifies a genuine actionable inconsistency, only then register a *different* one-rule pre-entry expression and its treatment/control cohort **before** opening another candidate wallet. Keep the same 1.5 statistic, fees/funding, manual starts, seven-day expiry, owned-fill and native-protection paths. Specify whether a veto consumes or merely defers an opportunity, and count later re-entry/missed winners; do not quietly inherit the held exit's no-minimum-age behavior. Compare with the old no-macro and prior entry-filter failures, and stop if the mechanism is a historical loser selector or merely reproduces a failed action family. Do not run 795 wallets, tune thresholds, relabel proxy P&L as native execution, or switch `main` on this screen.
