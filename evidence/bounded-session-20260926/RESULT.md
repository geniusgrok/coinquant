# 有限会话原生验收（未执行）

经济测量见 `evidence/rebuild-20260927/RESULT.md`。本文件只列原生交易所验收：代码已实现、离线已验证、真实账户上尚未验证的项目，以及验收步骤。`public/rules.json` 是 2026-09-26 从 Binance 公共接口读取的 BTCUSDT 合约规则，经济测量器用它作价格/数量过滤。

## 已实现

一个账户配置、一个 Binance 适配器、一条有限会话决策/执行链；默认300秒、5秒轮询，最长24小时，不留后台任务。执行器包含限价IOC入场、逐轮撤旧/重新定价、真实累计成交核对、资金预检与逐仓保证金补充、部分成交的 close-all 保护、保护替换、reduce-only 退出、部分退出后的余量处理、未知请求去重、完整成交归属、重启恢复与退出清理。撤单终态既核对原订单，也核对迟到成交；保护父单结束不等于子单结束。

输入未知、外部订单/成交、缺失归属、保护不明时不增加风险。状态和意图先持久化后发送；重试不生成新的操作身份。限流后进入冷却。

写请求结果分三类（2026-09-28 两轮复核后）：本地在发送前拒绝（权重预留、冷却、截止时间）记为 `NotSent`；写请求 HTTP 400/401 且错误码属于文档化的明确拒绝（`binance.REJECT_CODES`：-1021、-1022、-2010、-2011、-2013、-2014、-2015、-2018～-2022、-2024、-2025、-1100～-1199、一组明确的参数/余额拒绝码（不含 -4116 重复客户订单号、-4117 止损触发中）），或 Binance 文档规定为失败的 HTTP 503（JSON 错误体的错误码 -1008，或 `msg` 为 `Service Unavailable.`、`Internal error; unable to process your request. Please try again.`，见 `binance.FAILED_503`；代理或 CDN 的纯文本 503 不算）记为 `Rejected`；两者都把意图记为 `rejected`，表示交易所在该身份下没有订单或划转。其余错误（超时、`Unknown error, please check your request or try again later.` 及其他 5xx、-1006/-1007 等）保持未知，只能按稳定身份查询，不重发。保护、撤单、保证金和只减仓意图在 `rejected` 后可在同一身份下再试；入场永远换新周期，被拒入场不参与成交归属。

未知意图的结算：每个写意图在发送前记录适配器时钟的准备时刻。普通订单在准备 300 秒之后、1 天之内按身份查询得到 -2013，才记为未被接受（`Binance.absent_within_retention`）。查询失败、没有准备时刻、或已超过 1 天，都保持未知。条件单不使用这条规则。旧的、没有这条标记的“查无即拒绝”记录会在下次恢复时重新打开。只会降低风险的未知意图（保证金追加、只减仓单、close-all 保护及其撤销）只阻止新风险，不阻止保护与退出；在已核实空仓、无挂单/条件单/入场余量、没有可能增加风险的未决意图时，准备 300 秒后仍未结算的这类意图记为 `void`（`Lifecycle.retire_stale`），之后才允许新入场。`void` 只表示它已不能再改变敞口，不断言交易所从未接受（例如已执行的划转、空仓清理时撤掉的 close-all 单）。已有持仓时，未知的止盈腿不再阻止决策：恢复路径重新建立保护，保护回读失败则对自有持仓做只减仓退出（此前该状态只阻止）。可能增加风险的未知意图（入场、加仓）阻止一切决定，直到查询结算。

逐仓保证金划转没有客户端 ID：意图在发送前记录准备时刻，明确成功（`code=200`、类型1、金额相等）立即持久化为已确认，钱包回读不一致只报告未知；回答丢失时只从 `/fapi/v1/positionMargin/history` 结算（准备时刻前15秒至今、最长29天；恰好一笔等额用户追加，且没有其他未被拒绝的保证金意图在该窗口前15秒之后准备，才确认；否则保持未知。未记录准备时刻的旧意图按其最后本地更新时刻判断）。空历史不判为失败：历史出现延迟没有文档保证，这类意图只在已核实空仓时按上一段作废。金额按合约 `quotePrecision` 向上取整。

入场成交后的保护路径（`Lifecycle.enter`）：IOC 终态回读后，若自该入场空仓快照的成交 ID 游标以来（七天内无成交时改用该空仓时间边界的单个时间窗）的全部成交都属于这笔入场单、合计等于当前持仓（`Lifecycle.entry_fill_proven`），立即复用写后快照与入场预检时的合约规则补保证金并建立保护，完整归属审计随后进行并继续阻止新风险。离线真实适配器替身中，入场 POST 到首个止损 POST 之间的读请求由 54 次降为 12 次；这是读次数，墙上的秒数取决于每次响应的延迟。计划止损还在当前强平价外侧时，先挂一个紧贴强平价的止损，补上保证金后再换成计划止损。保护有 120 秒、保护失败后的减仓另有 120 秒保留网络预算（足够一次完整账户观察、成交证明与减仓写入在每次响应接近 8 秒超时时完成）。归属审计失败时，只有同样的成交证明成立才对该入场成交做保护；保护失败后的减仓也只在持仓仍等于该证明过的自有成交时进行；外部、人工或无法证明的持仓不写入。入场预检的合约规则只在 300 秒内复用，之后重读。

DFII10 只在能改变决定时读取（宏观仓、或空仓且没有未消费的主信号多头），主信号出场与保护维护不依赖它；两次请求共享会话剩余预算，失败后60秒内不重复请求。

`environment: demo` 使用 Binance 虚拟余额环境（`demo-fapi.binance.com`、账户 UID 读 `demo-api.binance.com`），凭据变量 `COINQUANT_BINANCE_DEMO_KEY`/`COINQUANT_BINANCE_DEMO_SECRET`，状态范围 `binance:BTCUSDT:demo:<uid>`，与实盘状态互斥。`capital_limit_usdt` 让仓位与保证金只按 `min(钱包, 上限)` 计算；它限制规模，不是亏损上限。

`research/session_replay.py` 是原生接口事件 tape 回放：复用生产 `session.run` 和 `Lifecycle`，严格匹配请求顺序、参数和时刻；它不是历史经济回放。公共接口已实测：合约规则、标记价格、100档盘口，以及从2019-12-01重建全部已完成4小时K线并从检查点续读（每页1000根、按官方档位计权重）。

## 原生验收执行顺序

1. 只读确认账户UID、单向/单资产/逐仓20x、钱包、无外部订单/持仓、最小数量和订单类型；不自动改账户设置。
2. 在获授权的小额上限内验证一次限价IOC、实际成交量、终态和 close-all 保护回读；若保护失败仅按已授权范围减仓。
3. 验证撤单/成交竞争及重新启动后的稳定身份回读；不故意让真实资金裸露来制造故障。
4. 对现有受保护的小额仓位验证新保护回读后撤旧；若交易所拒绝重复保护，保留旧保护并记录不支持，不能宣称可原子改单。
5. 正常停止后只读回读；确认无入场余单、保护仍在。退出测试资金并核对费用、资金费、成交和钱包闭环。

Demo 可以验证部分 API 语义，但不能替代生产撮合/流动性和资金风险验收。
