# Coinquant

个人使用的 Binance BTCUSDT USDT 本位永续交易程序。当前 SX60 + DFII10 模型只做多，定仓乘数为 7.5 / 3.6；它们不是亏损比例上限。使用单向、逐仓、20 倍杠杆账户。默认只读，手动启动有限会话，默认 300 秒，没有定时唤醒或后台守护进程。当前尚未完成修复后源码的历史经济验收和交易所原生 Demo 执行验收，不具备小资金主网试跑结论。

## 安装与配置

使用 Python 3.13，程序仅依赖标准库；系统需提供 `America/New_York` 时区数据。取得代码并复制配置：

```sh
git clone https://github.com/geniusgrok/coinquant.git
cd coinquant
cp config.example.json config.json
```

先填写 `config.json` 的 `account_uid`，使用核验一致的 Binance UID；`state_dir` 使用该账户固定的绝对路径或 `~` 路径。配置不存凭据。

| 字段 | 用法 |
|---|---|
| `environment` | `live`（默认）或 `demo`，账户、凭据和状态分别隔离 |
| `session_seconds` | 会话时长 1～86400 秒，默认 300 |
| `poll_seconds` | 轮询间隔 1～60 秒，默认 5，不超过会话时长 |
| `capital_limit_usdt` | 可选正值十进制字符串，限制用于定仓和持仓风险复核的资金；未设置时使用钱包余额，不是亏损上限 |
| `max_stop_loss_fraction` | 默认 `".10"`，有效值最多为 10%（更大的旧配置仍按 10% 限制），入场时冻结整轮到止损模型损失预算，持仓时另核对当前已观察权益到止损的预算；已成交部分计实际费用，未来部分采用当前 taker 费率 |
| `stop_slippage_fraction` | 默认 `".01"`，预算采用的止损逆向滑点假设，非实盘滑点上界；两项均为大于 0、小于 1 的十进制字符串 |

主网凭据从 `COINQUANT_BINANCE_KEY`、`COINQUANT_BINANCE_SECRET` 读取，Demo 从 `COINQUANT_BINANCE_DEMO_KEY`、`COINQUANT_BINANCE_DEMO_SECRET` 读取。两套凭据互不回退。

默认止损预算是已核实资金的 10%，另有硬上限：按止损再向外 10% 标记价留出的逐仓保证金不超过已核实资金的 25%；使用钱包、当前标记权益和配置资金上限中的较小值。追加同时计入交易所为新增仓位自动划入的初始保证金，并按结算精度保守取整。做不到最小数量就不开仓。未来资金费没有预先计入损失估计，波动目标使用当次 taker 费率。两字段同时设为 null 时仍可读取、保护和退出已有敞口，但禁止新入场或追加；已有仓的风险复核沿用可核实的冻结入场预算和滑点假设。资金上限、20×设置和止损在强平前都不替代这两条约束，也不构成连续账户回撤保证。

执行会话在持仓恢复后、入场或追加后及停止前复核实际风险，先于历史行情补读和宏观查询。已归属成交的实际手续费、已实现盈亏与已核实负向资金费都计入本轮成本；费用增加、权益下降或观察到的浮盈上升时，重新计算允许的止损。程序持久保存本轮净损失额度 `loss_ceiling_usdt`，只会收紧：已观察净浮盈扣除当前最多 10% 的模型回吐预算后，剩余额度通过更紧的原生止损锁定，额度可为负值表示按模型保留净利润。同一 campaign 的已接受止损不会因之后标记价回落或策略候选价较松而放宽，不追踪停机期间未观察的峰值。缺少实际费用、资金费或归属证据时保留现有保护、禁止追加，并报告持仓风险尚未核实。

持仓的逐仓保证金若超过当前 25% 资金上限，或预算所需的止损无法在当前价格与交易所规则内设置，会沿已有的仅减仓流程退出；退出受单次数量规则限制时分片完成。若强平价越过止损，或离止损的距离小于开仓时留下的缓冲，程序按新鲜可用余额在 25% 保证金上限内补保证金；补不上就退出。该缓冲固定为入场时的绝对价格距离，不因标记价上涨、换腿或补资而抬高目标。真实跳空、滑点、资金费变化或停机仍可使实际亏损超过模型预算，以上复核不是百分比硬亏损保证。

保证金恢复仍受当次资金上限约束；已经完成补资的旧计划也会重新检查。原计划需要的保证金不足时，不会把缩小的强平缓冲保存为正常基线。保证金接口没有请求身份，失联请求不能仅凭同额历史记录认定成功，也不会自动重发。程序核实实际缓冲已经恢复时保留受保护仓位；缓冲仍不足且成交归属完整时继续仅减仓退出。未决身份仍阻止新增风险。

## 只读运行

```sh
python3.13 -m coinquant status --config config.json
python3.13 -m coinquant run --config config.json
python3.13 -m coinquant snapshot --config config.json --out /tmp/coinquant-snapshot.json
```

`status` 读取一次账户和合约条件；`run` 在期限内观察、恢复订单状态、判断策略并输出预览。`snapshot` 导出新鲜只读账户 JSON，输出文件必须不存在。只读命令仍会保存本地核对记录。

首次 `run` 从固定的 2019-12-01 UTC 起点重建完整四小时行情，逐页保存 checkpoint；有限会话内未完成时可再次人工运行继续。行情重建不会补造历史成交，冷启动不会追入已存在的信号。

## 有限交易试运行

以下命令中的尖括号占位符须换成专用账户 UID 和实际订单 ID。

```sh
cp config.demo.example.json demo.json
python3.13 -m coinquant run --config demo.json
python3.13 -m coinquant run --config demo.json --execute --trial demo --authorize-uid <DEMO_UID>
```

填写专用 Demo UID、固定状态目录和正值资金上限。执行需同时提供 `--execute`、与配置中显式 `environment` 一致的 `--trial` 和匹配账户的 `--authorize-uid`；入口不会强造策略入场。

主网试运行使用 [config.live-trial.example.json](config.live-trial.example.json)，还需 `--trial live --demo-evidence <JSON>`。Demo 验收后用只读命令采集证据：

```sh
python3.13 -m coinquant demo-evidence --config demo.json --out demo-evidence.json \
  --entry-order-id <ENTRY> --stop-algo-id <STOP> --take-algo-id <TAKE> \
  --reduction-order-id <REDUCTION> --offline-trigger-order-id <TRIGGER>
```

命令核对 Demo 专用 UID、持久状态中的原始委托、交易所原生订单与成交，以及 SQLite 和观察归档中的会话报告；要求止损和止盈各自的真实触发、终态子单和逐笔成交，保护回读、部分仓位减仓、停机后触发与再次启动核对。正常全部成交但仅减少部分仓位的减仓单也可验证，须有该原身份发送前的已核对仓位记录；只出现部分成交状态不够。必需订单须有当前源码版本 Demo 会话中的原身份与发送时间记录；恢复旧版仓位不会把旧版委托算作新版验收。证据只保存在本地，主网入口会重新做只读 Demo 核对，单独填写订单 ID 不会通过。Demo 证据资金上限须不低于主网试运行上限，止损预算和滑点配置须与主网一致，且实际发单与完成会话的报告也必须记录相同配置；将主网两项预算设为 null 只关闭新增风险，仍可用原配置的同源码 Demo 证据管理已有敞口。采集和核对需要用户另行授权的 Demo 账户访问。源码或执行配置变化后，不沿用不匹配的证据。

会话记录保留报价、请求与回读时间和实际成交；可回读成交价时计算保护触发滑点，缺项不按零成本补值。离线软件检查或只读快照不能证明真实委托、止损触发和重启执行已经通过验收。

执行先持久记录订单身份，成交后确认交易所托管的整仓止损和止盈。丢失回包时查询原身份；未解释的成交、资金或保护状态阻止新增风险。会话到期或中断后停止开仓，清理最多延续360秒，提前停止也按实际停止时间收紧总期限；确认的原生保护留在交易所。已证实终态部分减仓且新鲜成交归属证明残仓缩小时，可在总期限内使用新身份继续减仓；未知结果不换身份。已归档且仓位、方向和归属不变的零成交退出，每次人工会话最多换一次新身份重试，清理阶段共用这次额度；仍无进展则保留状态等待核对，下次人工会话重新核对后才可继续。有实际部分成交进展的退出可继续分片。

## 状态、停机与恢复

原生整仓止损或止盈开始实际成交后，终态部分成交的残仓继续退出，不在同一会话买回。清理已平仓的保护腿之前逐次重新核对账户，外部重新开仓会阻止撤保护。父条件单已报告成交却没有可核实子单时保持未决，不把“父单已取消”当成没有成交。

固定 `state_dir` 保存 `intents.sqlite`、`latest.json`、观察归档和执行锁；账户锁还保存在 `~/.local/state/coinquant/account-locks`。同一账户只使用一台机器、一个客户端。重启继续原订单身份；保留原状态目录和观察归档，状态不匹配时只读核对，不删除数据库、不改 UID 或换空目录绕过。

当前模型状态协议为 v7，SQLite 状态协议为 1。v7 记录价格止损刺破、策略止盈和到期退出的原因；尚未完成的价格止损退出必须保留同一 campaign 的原有期限和保护几何。同为 v7 但已丢失这些字段或几何的旧状态也会拒绝恢复，不能凭空补回。字段布局、版本、校验值及现有恢复校验全部匹配的 checkpoint 可以原目录继续运行，不迁移数据库或重建 checkpoint。旧的 v6 布局在订单恢复和清理前拒绝，不补默认值、不清库重建。升级前停止会话、保留匹配旧版源码，并在进程停止后备份完整原状态目录。不兼容旧版的持仓、余单、未决意图或保护替换，须继续用匹配旧版和原目录核对、管理，或由账户所有者人工处理；平仓也不自动迁移未知布局。新版 `status` / `snapshot` 可只读观察当前仓位、订单及保护，仍会更新本地核对记录，不能证明完整历史成交归属。不得篡改版本或校验值、改 UID 或换空目录接管旧持仓。

保护替换恢复继续使用原操作身份；正式保护已接替临时保护时，不重新使用已撤掉的临时腿。每腿第一次真实 NEW 回读时间保存在原意图记录中，完整保护保存与完成入场计划一起提交。若在两步之间停机，只有当前同一原生身份仍为 NEW、且首次回读时间或原生创建时间可核实时，才恢复其历史覆盖；只读运行同样遵守，不会先跳过历史条件再保存行情进度。仍持有的宏观仓位遇到只读失效观察时保留原几何及退出原因，后续宏观恢复只清除对应宏观退出，不取消独立价格或期限退出。

启动时间和间隔由自己决定。每次 `run --execute` 先核对实际持仓、原生保护及成交归属，维护当前可核实的持仓风险，再从保存位置补齐已经完成的四小时 K 线，按当前账户和行情处理到期、价格条件、跟踪止损及宏观状态。补读历史只恢复模型状态：本次风险维护或补读算出的新止损在交易所确认接受之后才生效，过去的 K 线不会被当成已经受该新止损保护。尚未补读的旧保护几何保留到对应行情检查完成，行情分页中断或再次换腿不会抹掉之前已经成立的条件；跨不同保护几何交接的 K 线，不凭高低点猜测触价与换腿的先后。需要退出时在本次实际运行时发单，成交只认交易所记录。不带 `--execute` 的 `run` 可以补齐模型和展示预览，但不会维护交易所保护或完成策略退出。

SX60 的七日期限从信号计时；期限届满后的条件由下一次运行补读、判断并在当下处理。已记录成交价的多头若在该期限的已完成 K 线仍比成交价高出至少六个初始风险单位，则改为过去 14 天最低价的跟踪止损，且不低于成交价，原止盈不再作为退出。跟踪止损在已保存的止损之上更新，按需运行时才向交易所提交。价格止损刺破只在最终标记价仍越过当时生效的止损时市价退出；标记价反弹时保留原期限和跟踪状态。七日到期和成交价 K 线触及模型止盈的主动退出维持原策略语义，不以止损反弹取消；原生条件单仍使用 MARK_PRICE。下跌脉冲不占信号槽，也不开空。没有成交价记录时仍按七天期限处理。

会话结束时可以保留已确认受原生保护的持仓。进程停止期间只有最后已接受的交易所原生保护可能执行；到期、14 日低点跟踪、宏观退出和本地风险复核留到下次人工运行。运行间隔越长，这些响应越晚，实际成交、资金费、收益与回撤也会改变；经济比较须使用实际约定的启动日程。下一根完整四小时 K 线提示新的模型复核机会，宏观数据或订单变化也可能更早需要检查；报告不会预约后台任务。有较大浮盈时，即使止损没有下移，停机期间从峰值回落到最后已接受保护的损失也可能使权益回撤超过 50%；四小时高点不是逐笔高点。这不是连续回撤合格的证明。

`model_caught_up_through_ms` 表示模型已经补齐到哪根完整 K 线，`next_strategy_candle_at_ms` 是下一根可复核的四小时收盘时间。持仓且这根 K 线已经完成时，`strategy_catchup_due=true`；`review_due_now` 还包括需要人工核对的未解决状态。这些字段描述模型进度与当前复核需求，不是定时启动任务，也不证明对应期间持续执行过保护维护。

停止报告的 `native_protection_at_stop` 给出最后一次观察时间和保护腿：`flat` 为已观察平仓，`observed` 为当时两腿完整且止损在强平前，`incomplete` 为保护不足，`unverified` 为本次未能确认。它不保证之后保护不会触发或被撤。`holding_risk` 另外记录持仓成本和预算复核：`observed` 表示本次最近已核实观察的模型风险，`last_observed` 表示保留的旧观察，`flat` 为已观察平仓，`exit_pending` 为风险退出尚未完成，`unverified` 为尚未完成本次复核。只读运行不将旧记录算作本次已完成维护；`holding_risk_review_required` 提示需要继续检查。风险记录保留计算时的标记价和观察时间，不宣称之后价格或资金费不变；原生保护存在也不等于当前费用和权益仍符合预算。

`pending_intents`、`unresolved_order_ids`、`protection_replacement_pending` 和 `execution_unresolved` 标示未决身份、未完替换及未解决执行；`pending_intents=0` 不证明残仓有保护。持仓且策略核对失败时另有 `strategy_review_required`。`manual_takeover_required=true` 时保留原目录，核对错误原因、交易所仓位、普通单与条件单，必要时由账户所有者处理敞口；它不要求盲目平仓，未知身份不得重发。明确配置或状态不支持会显示 `blocked`，订单或读回不明显示 `unknown`。运行时不要并发手工交易；停机后要手工重开仓，先核实并清理旧 closePosition 保护，否则旧腿可能平掉新手工仓。

持有仓位时，恢复对账依赖原 `state_dir/intents.sqlite` 中的订单身份、原生成交和历史覆盖记录，以及交易所可回读的订单、保护子单和从已核对边界至今连续的 BTCUSDT 成交。未覆盖的区间若超出最近约三个月的原生查询窗口，或子单终态、成交归属无法证实，程序会报告 `unknown` 并阻止新增风险；不会靠价格推断补齐。保留原状态目录，核对原环境与 UID、订单及子单身份、成交和当前仓位与保护状态，必要时人工处理敞口；不要换空目录、篡改覆盖记录或重发身份未明的订单。

历史 algo 查询缺失时，只以新鲜活动列表中逐字段匹配、尚未触发的 NEW 父单作为活动证据，不伪造终态。正常维护会在真实原生创建时间达到75天且仍小于90天时，沿现有先新后旧路径续期相同保护几何。停止跨过这个窗口后，超龄 NEW 仍可能保护仓位且可用于归属核对、退出；撤单或触发后若历史已不可回读，活动列表中的缺失不能证明终态，清理仍可能 `unknown`，需人工核实。超龄腿的破坏性替换不自动进行。

`snapshot` 的价格距离损失不含手续费、滑点或跳空，不能当亏损上界。SX60 和 DFII10 共用一个单向持仓；每次原生入场按新鲜已核实权益、双边手续费和指定逆向滑点估算整轮到止损损失，并受 10% 损失预算与 25% 逐仓保证金上限约束，DFII10 另有 3% 模型预算。发单前重新核对盘口价格、可执行深度、成交游标和会话期限；最终标记、盘口事件时间或发送时的交易所时钟跨过下一根四小时收盘时，先补齐模型再增加风险。持久化准备之后也检查报价有效期和会话停止条件，耗时不会延期开新仓。开仓与追加的可用余额检查包含入场价相对标记价的不利价差。原会话追加同时受冻结入场 USDT 预算和当前标记权益到止损预算限制，计入浮盈回吐，不因盈利放大冻结预算，也不借未实现利润付保证金。整轮预算累计所有已归属成交的实际 USDT 费用和已实现盈亏，并在追加时扣除本轮已核验的负向资金费；部分减仓不会退还已付费用或抹掉已实现亏损。未来成交按当前费率估计，已付费用不从现金再次扣除。追加前资金流水必须与本次观察的钱包闭合，即使资金费与入金或利润抵销、钱包数值不变也要核对。资金费范围从持久化的本轮入场准备边界开始，保留 15 秒的保守重叠；收到的资金费和入金不会补回冻结预算。只刷新流水不会延续旧的钱包闭合证明。实际费用、盈亏或资金费证据缺失，流水区间或币种不明，预算未知或成交归属不完整时禁止追加；保护与退出继续按原有归属条件处理。跳空、真实滑点、多笔累计亏损和停机期间浮盈回吐仍可能突破预算。历史模拟不能证明实盘能力或未来收益。本项目独立运行，不要求与其他项目同步启动或合并账本。报告里的 `close_position_client_ids` 是当时挂着的全仓条件单；`protection_replacement_pending` 同时看会话替换和未完成的保护替换。能产生成交的未知订单只有在保留期内收到 -2013、活动列表没有它、且期间成交都已归档时才会作废。确认过的零成交减仓按上述每会话额度处理，未知结果不重发。条件单父状态为 TRIGGERED 时，只有实际子单也已确认终态才允许归档、处理残仓和清理保护；单独的 TRIGGERED 不是完成证明。

报告将20×设置、`wallet_notional_ratio`（名义/钱包）和 `account_notional_leverage`（名义/同次标记权益）分别列出；非正分母返回 null，`equity_status` 明示非正权益，不把钱包当全账户权益。出现 `blocked` 或 `unknown` 时根据报告核对配置、原状态和交易所订单；无法确认的敞口需人工处理。若缺少 `America/New_York` 时区数据，安装系统时区数据库，或运行 `python3.13 -m pip install tzdata` 后再启动。
